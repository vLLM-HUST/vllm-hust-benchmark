# M01 诊断采集与主机计数恢复

## 第四轮设备长度补采

保持相同 B1 配置及 200 请求，使用独立缓存。请求全部成功，输入 282265、输出 51200 tokens；881 个调度波次关联通过。两卡各保存 1758 条设备长度记录，覆盖 879
个采样波次的两个 MTP 步，记录身份及长度逐条一致，采集错误和绑定错误均为 0。客户端退出码为 0，服务清理退出码为 130，进程组及四卡均释放。

启动前的小规模 NPU 测试验证了 8 组“上传等待、长度复制、图重放、最终回读”的数值一致性。该测试不加载模型，不代替完整模型运行时的流顺序证明；原始
`stream_order_qualified=false` 保留。

同轮关联全部 19434 条请求行后，19292 条有输出记录均满足“第一步 KV 长度 = 累计 prefill + 此前保留输出 + 调度草稿数”。81 条无输出行也吻合；其余 61
条只在输出已达 256-token 预算后多一个槽位，单独保留，不计作新增有效输出。第二步 query 长度为 1，KV 长度等于第一步加 1；按本波次拒绝数缩短第二步 KV 的假设会与 4334
条有输出记录冲突。

本轮保留草稿为 32042 tokens，不复用第三轮的 32062。设备 KV 长度、采样位置和最终保留输出是不同量，不能相互替代。有效草稿上下文归属、完整 F 和独立参考时间仍未闭合，M01
不作达标判定。

## 测试对象与方法

受测对象为 Qwen3.5-35B-A3B、BF16、TP2 的 vLLM-HUST 组合优化方案， 采用 E24/R36、KV materialization recompute 与 Prefill
Microflow。 沿用既有 200 条 MMLU-Pro 输入和每请求 256 token 输出预算。 本轮启用主机调度、输出保留及 GDN 元数据采集，不属于无插桩性能测量， 也不是官方
vLLM 0.18 / vLLM-Ascend 0.18 B0。

## 结果

第一次采集在请求处理结束后失败：客户端 RPC 白名单未包含新增的 worker 导出方法。双卡导出未执行，客户端退出码为 1，服务清理退出码为 130。
进程组与设备均已释放。调度器退出导出成功，原始文件及失败日志保留。 异常发生在 benchmark 汇总文件序列化之前，因此没有正常的结果 JSON， 不能仅凭进度条认定请求质量或完整性能验收通过。

按同主机时钟边界从调度器记录恢复的输出计数如下：

| 项目                 |  数值 |
| -------------------- | ----: |
| 窗口内请求身份       |   200 |
| 追加输出 token       | 51200 |
| 每请求追加输出 token |   256 |
| 原始接受草稿 token   | 32120 |
| 最终保留草稿 token   | 32064 |
| 末尾裁剪草稿 token   |    56 |

140 条未更新记录中，16 条出现在首次输出之前且未调度草稿，124 条出现在 请求已完成 256 token 输出预算之后。此分类只证明它们没有新增保留输出； 首次输出之前的记录仍可能包含有效
prefill 计算，不能按零 FLOPs 处理。 原始 `retained_count_complete=false` 不改写，分类结论另存为派生证据。

## 结论与限制

第一次采集提供部分主机计数，不提供完整有效算量、独立参考时间或 M01 达标率。 不得将本轮计数与另一轮未插桩耗时拼接计算。当时仍缺双卡波次元数据和完整 同工作量核算。后续修复新增了严格限定的导出
RPC，并在导出之前持久保存 请求响应及逐 token 时间；修复测试不代替真实补采验收。

归档分别保留各轮修复前源码、失败原始证据与计数恢复、后续保护及分类代码。 `manifest.json` 校验归档和全部文件成员。归档中的绝对路径用于定位原实验环境，
不是部署配置。原始数据不覆盖、不重新标记为成功。

## 第二次采集

第二次采集使用独立输出及编译缓存目录，保持原服务参数与输入不变。 `request-checkpoint.json` 在诊断导出之前保存了 200 条成功响应，共 51200 个 输出
token，以及原始文本和逐 token 时间。成功响应不等同于任务评分通过。

两卡各导出 882 个执行波次和 881 个采样阶段，但各有 881 次 `host_gdn_metadata_invalid`，异常类型为 `KeyError`，故导出标记为不完整。
采集器依赖运行时函数签名绑定参数，而实际插件包装层采用 `*args/**kwargs`， 不能从该签名取到原生 `num_reqs` 参数。此轮未获得有效 GDN 元数据。

本轮也缺少调度器退出导出；Manager 默认 10 秒退出宽限期短于服务的 60 秒， 而导出位于 worker 清理之后。后续修复采用固定原生 ABI 绑定参数、提前保存 调度器记录并延长
Manager 退出宽限期；尚不能由离线测试认定补采通过。

客户端退出码为 1、服务清理退出码为 130，进程组和设备均已释放。 完整有效算量、独立参考时间及 M01 达标率仍未确定，不以本轮诊断耗时替代 无插桩性能结果。原始失败状态和完整性标记保持不变。

## 第三次采集

固定原生参数绑定和退出导出修复后，使用独立缓存完成同一工况的 200 条请求，失败数为 0，输入 282265 tokens、输出 51200 tokens。两卡各取得 873 条有效 GDN
主机元数据；调度器与两卡的 874 个执行波次关联通过，错误和丢弃均为 0。客户端退出码为 0，服务清理退出码为 130，进程组和四卡均已释放。原始文件 SHA256 全部验证通过。

同轮请求边界内，原始接受草稿为 32129 tokens，最终保留 32062 tokens，其中第一位置 17305、第二位置 14757，末尾裁剪 67 tokens。128 条未更新行中，18
条在首次输出之前且没有草稿，110 条在输出预算完成之后，无未归类项。此分类不代表首次输出前的计算为零，原始 `retained_count_complete=false` 保留。

本轮补齐双卡元数据与调度器关联证据，但尚未完成全部有效算量及独立参考时间核算。诊断采集成功不是 M01 达标；计数不移植到其他未插桩轮次。请求成功也不等于任务质量评分通过。

## 有效算力与效率

实测单芯片平均有效算力为 `C=F/(k*T*10^12)`；同一有效工作量和参与芯片数下，参考有效算力为 `C参=F/(k*T参*10^12)`，因此
`η=C/C参*100%=T参/T*100%`。

`η≥50%` 表示达到同工况参考有效算力的 50%，不是芯片标称峰值的
50%。参考时间须由独立标定和模型依赖推导；未经证明不称严格时间下界或算力上限。不由实测耗时反向拟合参考值，不扣减估算的插桩开销。本目录的 F、参考时间、参考算力和达标结论均尚未确定。

## 第三轮算量复核

双卡分别恢复出 218 个 prefill 片段，覆盖 200 个请求、282265 个输入 tokens；逐请求长度、片段顺序及初始状态一致。64-token 分块列表与实际元数据吻合。采用已列出的
H/O、扫描、KKT/WY 和三角逆运算公式，得到 prefill 基本运算候选小计 37779616201920；特殊函数与比较不赋予任意 FLOP 当量。

从本轮输入输出重新计算的目标模型已列运算项候选小计为 1768655972286925。保留草稿的词表投影子集为
32610860400640，单独列示，不替代草稿上下文和注意力运算，也不与目标小计相加宣称完整 F。

调度记录与双卡元数据关联了全部 19409 条请求行，其中 19281 条有输出、128 条未更新。根据 `prepare_inputs_padded` 的源代码公式可推导候选采样位置及 6033
条被拒绝填充行；该推导尚未证明实际分支选择、草稿缓存生命周期和后续位置，因此不构成有效草稿算量结论。以上均为同轮离线核算，不使用其他轮次耗时。

归档。当前仍缺完整有效算量及独立参考时间，M01 不作达标判定。
