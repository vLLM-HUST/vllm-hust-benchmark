# 10 月 26—27 日：从串行实验到高效 P/D 服务场景的模拟进展

这两天的工作，围绕两个问题展开：原真实实验的 D 端改成并发后会怎样；Tailguard 的调度收益能否在合理的并发基线上成立。

主线是：先发现 D 整请求串行限制，再发现小容量与缓存交接问题；补充硬件标定、让缓存变化重新参与模拟后，区分了扩容和并发的影响；最后引入高效服务的参考流程，发现原来的请求注入量不足以压出资源饱和点。

涉及三种证据：原两节点历史实测、新增单机标定/验证、CPU 上运行的模拟。以下按研究推进顺序说明；模型和服务流程发生变化的阶段分别标注。它们构成研究过程，不是一条可以直接累计的性能优化成绩。

**1. 起点：原真实实验等待很长，发现 D 被实验实现限制为串行。**

原实验使用 Qwen2.5-7B-Instruct、BF16、2P2D、95 条请求和 8 个会话。基线前后各跑一次，中间包含历史策略组。

| 历史实测组       | 平均 TTFT |     p95 | p99 / 最大值 |
| ---------------- | --------: | ------: | -----------: |
| 前基线 B-before  |   35.58 s | 66.82 s |      75.37 s |
| 历史策略组 T-off |   33.37 s | 48.34 s |      57.60 s |
| 后基线 B-after   |   41.13 s | 83.32 s |      86.76 s |

T-off 指关闭慢速布局规划、保留历史快速路径的组。B-before/B-after 是相同基线的两次运行，用于观察运行状态漂移。

排查代码发现，串行限制存在于多层：引擎 `max_num_seqs=1`、控制器每卡一个执行线程、worker 的锁覆盖整次请求。此外，CPU 池和 NPU KV 都只有每实例 2 GiB，token
预算为 128，使用 eager 模式。

因此，D 要等前一条请求完整生成结束，下一条才能进入。前基线的平均 D 准入等待约 25.2 秒，是长 TTFT 的重要来源。这首先暴露的是实验原型的执行限制。

来源：[初期离线模拟记录](provenance/initial-concurrency-report.md)、[原配置验证](../pegaflow-pd-serial-validation-20261027/README.md)。

**2. 第一版模拟：只让 D 并发，平均等待明显减少，长尾仍然较大。**

资源不足时，先用前基线、历史策略组、后基线共 285 条实测记录做离线模拟。保留实际路由、缓存命中和分段服务工作量，改变 D 的并发上限，P 保持串行。

当时没有硬件合批曲线，示例采用“4 路合批一步约为单路 2 倍耗时”的假设，同时分析其他效率情景。

以前基线为例：

| 固定历史行为的回放 | 平均 TTFT |     p95 |     p99 | 全部完成 |
| ------------------ | --------: | ------: | ------: | -------: |
| D 串行             |   35.58 s | 66.82 s | 75.37 s | 725.33 s |
| D 并发 4           |   18.23 s | 53.40 s | 63.41 s | 542.40 s |

发现：并发可以显著减少整请求串行造成的排队，但最慢请求改善有限。每 D 2 GiB NPU KV 容不下多个长请求的完整工作集，还会造成容量准入等待。

随后仅将这一版模型的 NPU KV 放宽到 16 GiB，平均 TTFT 约为 16.73 秒，p99 为 49.41 秒。这个变化用于检查 NPU 容量影响；CPU
缓存行为和每条请求命中仍按历史固定。

这一阶段支持“需要合理并发与显存预算”的判断，还不能预测并发后真正发生的缓存淘汰与恢复边界。串行回放与实测接近到浮点误差量级，是因为用了同批实测服务时长，只证明时序记账接对了。

来源：[初期离线模拟记录](provenance/initial-concurrency-report.md)。

**3. 补实机标定：确认合批有效，也确认 eager128 不是高效服务的合理主配置。**

拿到单机资源后，测量不同长度、batch=1/2/4/8 的真实计算步耗时，并采集调度、缓存页、内存拷贝和资源活动数据。

主要发现是：

- eager128 的纯 decode 整批单步约 54–60 ms；graph2048 约 18–35 ms，随上下文和 batch 变化。
- 单机测量窗口内，eager 组 AI Core 活动均值约 39%–41%；graph2048 组约 87.6%。图执行与 token 预算同时改变，不能将全部差额只归因于一个开关。
- 每卡 64 GiB HBM 并不要求把 NPU KV 限制为 2 GiB。16 GiB KV 的图模式实测整卡峰值约 34.5 GiB。
- CPU↔NPU 保存与恢复也有可观的描述符、提交和同步成本，需要单独建模。

用实测合批曲线替换早期效率假设后，固定历史行为的 D4 / NPU KV16 GiB 示例结果为：

| 历史工作量样本 | 平均 TTFT |     p95 |     p99 | 全部完成 |
| -------------- | --------: | ------: | ------: | -------: |
| 前基线         |   16.88 s | 46.75 s | 48.61 s | 517.32 s |
| 历史 T-off     |   16.95 s | 37.63 s | 55.73 s | 474.76 s |
| 后基线         |   19.48 s | 54.36 s | 59.18 s | 589.80 s |

这一版仍含“25% 的历史 decode 成本不能共享合批收益”的展示假设，另测了其他比例。

发现：合批带来的平均等待改善比较稳定，但策略组相对基线的结果没有形成统一优势，而且前后基线本身有漂移。由于三组使用各自历史工作量、命中和路由，该表不能证明 Tailguard 在新的并发基线下有效。

来源：[硬件标定记录](provenance/hardware-calibration-report.md)。

**4. 升级模拟器：从重排历史耗时，推进到按计算步和缓存页预测。**

进一步发现，若命中和工作量始终冻结，就无法回答“改变缓存容量或调度后，系统究竟会发生什么”。因此增加按调度步计算成本、按实际 token 增长 KV 页、前缀共享、引用计数、释放与淘汰的模型。

先在单引擎上验证：32 个标定输入用于拟合，另外 95 个输入用于开发验证。

| 单引擎验证场景 | 平均 TTFT：实测→模拟 | 全部完成：实测→模拟 |
| -------------- | -------------------: | ------------------: |
| 私有前缀       |        33.19→32.47 s |     107.08→105.67 s |
| 共享前缀       |        17.27→16.82 s |       52.61→51.66 s |

对应平均 TTFT 偏差约为 −2.2% 和 −2.6%，活跃 KV 页峰值及共享组命中量也得到重现。该阶段说明计算和 NPU 缓存子模型在这些已观察工作负载上可用。

这些单引擎请求在约 7.5 秒内集中进入，输出长度也不同于原两节点回放。其时间不能直接与原两节点约 197 秒展开的注入过程比较；单引擎误差也不是完整 P/D 模型的误差界限。

来源：[单引擎标定与开发验证](../pegaflow-step-simulator-20261026/README.md)。

**5. 排查长尾：P 算完不代表 D 一定拿到，CPU 缓存池也必须重新模拟。**

沿着长请求检查发现，不能只关注 NPU 容量：P 完成的 KV 需要在 CPU 池保留到 D 恢复时刻。此前标为“16 GiB”的固定历史行为模拟，只放宽了 NPU KV，并未重新产生 CPU
缓存命中。

于是先按原配置重新推演一次完整基线：从输入、原初始 CPU 库存、到达时间和测试前成本模型出发，让缓存发布、回收和 D 恢复边界重新产生。

| 原配置验证   | 平均 TTFT |     p95 |     p99 | 全部完成 |
| ------------ | --------: | ------: | ------: | -------: |
| 原前基线实测 |   35.58 s | 66.82 s | 75.37 s | 725.33 s |
| 原配置新模拟 |   39.62 s | 68.40 s | 71.50 s | 736.49 s |

相对前基线，平均 TTFT 约高 11.3%，逐请求绝对误差均值为 5.90 秒。因此，该模型可以帮助解释机制，但逐请求预测仍有明显误差。

新模拟中，`feal-differential-cryptanalysis:12` 在 P 完成时有 180 块缓存；等待 D 期间，后续写入触发小 CPU 池的 292 块回收，使其连续前缀从
180 块降为 0，之后只剩共同前缀 5 块。因此 D 最终只恢复 640 token，并大量补算。

这是模型重新产生的缓存丢失链条；确认原实机全部细节仍需要原运行的逐块日志。

来源：[原配置串行模拟验证](../pegaflow-pd-serial-validation-20261027/README.md)。

**6. 将 CPU 池和 NPU KV 同时扩到 16 GiB，再观察 D 并发。**

这次扩的是每实例两种容量，并重新计算命中和恢复边界。

| 重新推演缓存的模拟场景 | 平均 TTFT |     p95 |     p99 | 全部完成 |
| ---------------------- | --------: | ------: | ------: | -------: |
| CPU2 / NPU2 GiB，D1    |   39.62 s | 68.40 s | 71.50 s | 736.49 s |
| CPU16 / NPU16 GiB，D1  |   35.46 s | 52.71 s | 54.30 s | 642.02 s |
| CPU16 / NPU16 GiB，D4  |   19.90 s | 44.73 s | 63.78 s | 539.48 s |

扩容后，D 补算总量由 473,958 降到 5,990 token，减少 98.7%。95 条请求都恢复完整可恢复块，CPU 容量淘汰消失。上述长请求恢复量由 640 增至 23,040
token，只剩 63 token 要补算。

发现：容量问题得到缓解，D4 的平均延迟与总完成时间进一步改善，但 p99 比同为 16 GiB 的 D1 更高。P 整次 API 锁、缓存交接等待，以及 D
内部恢复与混合服务仍会影响长尾。平均请求内 TPOT 也从约 60 ms 增至 118 ms。

继续把 CPU 池加到 32 GiB，结果与 16 GiB 相同。这份工作集的 CPU 峰值约 4.55 GiB，继续扩容已没有收益。下一步需要检查整个服务流程的效率。

来源：[CPU 扩容与 D 连续批处理模拟](../pegaflow-pd-capacity-batching-20261027/README.md)。

**7. 切换到高效服务参考流程：同时使用图执行、两端批处理和分层缓存。**

按服务效率目标更新参考场景：P、D 两端连续批处理，并发上限 128；启用图执行和 NPU 前缀缓存；CPU 池每实例 24 GiB，NPU KV 按显存预算估算为每实例约 38 GiB；P/D
token 预算为 8192/2048；采用异步 CPU 保存、RDMA 交接和 NPU 恢复。

这一步的模型也发生了变化：计算改用图模式按步标定，CPU 保存/恢复改用独立组件测量，交接采用目标异步流程，D 要拿到完整可恢复前缀。

| 目标服务流程预测   | 平均 TTFT |     p95 |     p99 | 平均 TPOT | 全部完成 |
| ------------------ | --------: | ------: | ------: | --------: | -------: |
| P8192 / D2048      |   0.247 s | 0.502 s | 0.970 s |  19.60 ms | 202.34 s |
| P2048 / D2048 对照 |   0.258 s | 0.571 s | 1.086 s |  19.61 ms | 202.34 s |

P8192 有 21 个计算步超出 token 标定范围；P2048 对照的计算步在标定范围内。完整两节点连接器、CPU 竞争与异步交接开销仍需实测验收。

从上一阶段到这一阶段，既改变了配置，也改变了缓存复用、服务流程和成本模型。因此，19.90 秒与 0.247 秒的差额不能直接认定为实际代码已经获得的加速，更不能归因于
Tailguard。这一预测代表高效目标流程下的估计。

来源：[高效 P/D 服务参考场景](../pegaflow-pd-serving-scenario-20261027/README.md)。

**8. 最新发现：原请求注入量不足，尚未压出真正的资源饱和点。**

高效参考场景下，并发上限虽为 128，每个 D 实际最多只有 3 条请求同时运行，全系统在途峰值为 6。CPU 和 NPU 均无缓存淘汰，模型中的 RDMA 服务队列无等待。

原负载只有 8 个会话，同一会话下一条要等上一条完成，理论在途最多 8 条；名义到达速率约 0.49 req/s。最后一条名义到达在第 197.47 秒，全部完成在第 202.34
秒，整轮时间主要跟随输入时间展开。

此时应区分耗时来源与饱和瓶颈：

- 首 token 延迟：P 计算与结果交付平均 143 ms，占约 58%；CPU 保存、交接和恢复合计约 53 ms。
- 完整响应：平均 2.74 秒，其中首 token 后 D 生成约 2.49 秒，占约 91%。
- 排队压力：P/D 入场排队平均合计约 4 ms，尚未测到硬件资源饱和点。

来源：[TTFT 百分位与阶段耗时](../pegaflow-pd-serving-scenario-20261027/TTFT-ANALYSIS.md)。

**目前的成果与下一阶段。**

已经形成了三类阶段成果：真实硬件的计算/缓存组件标定、经过单引擎开发验证的调度与 KV 模型、能重新产生 CPU 缓存行为及 P/D
交接时序的模拟。实验实现中的串行、小缓存和低效服务配置得到区分，扩容能解决哪些问题也有了对照。

优化调度的最终效果仍待同条件比较。下一阶段固定高效服务基线，增加独立会话及真实请求注入速率，记录从低负载到饱和的变化；在相同配置、工作负载、交接语义和成本模型下比较基线与
Tailguard，再用实际两节点运行验证关键条件。

本目录 `summary.json` 保存从各阶段数值产物抽取的汇总；`provenance/` 保存早期本地报告快照。所有阶段每组仅 95 个请求的 p99 均按 nearest-rank
计算，等于该组最大值，应结合 p95、逐请求时间线及模型边界解释。
