# 驱动接收之后的任务推进对照

本轮追加 47 次完成的原生恢复、5 次有完整结果的独立 CANN 队列标定，以及两项未完成记录。
原件为 `raw/queue-driver-2150.tar.gz`，113 个成员及摘要见同名 manifest。
复算入口为 `analysis/analyze_queue_driver.py`，结果为 `analysis/queue-driver-summary.json`。

## 结论推进到了哪里

本轮将部分慢调用的范围，从“批次 API 返回之后”进一步收敛到
**驱动已经成功接收任务之后、设备可见队列继续推进之前**。
它解释了为什么上层已经提交、CPU 还在忙等，而实际 DMA 之间仍有空档。
目前尚不能在驱动软件队列转发、内核调度及设备任务调度之间唯一定位触发条件。

软件资源环在正常节点也会满，因此“资源环满”本身不是根因证据。
真正不同的是：同类积压在正常节点较快推进，在慢节点可驻留数秒。
本轮没有交付生产修复，也不将带诊断采样的绝对耗时替代日常运行性能。

## 实际环境与固定负载

- 91：原慢宿主机 `host-192-168-0-2`，逻辑 0/1 对应物理卡 2/7，分别属于 NUMA 6/2。
- 81：用户重启后仍为 `host-192-168-0-4`，本次逻辑 0/1 对应物理卡 **5/7**，均属于 NUMA 2。
  此次分配与早先物理卡 4 的记录分开保留。
- 每容器两张 910B2、8 核 CPU、64GiB 内存；每个节点同一时间只测一张卡。
- 使用原生缓存服务和跨进程 NPU 张量导入，不运行模型、不使用 RDMA。
- 每次恢复 161 块、3.773GiB、15,456 个 256KiB 描述符，96 个平面；源池 5GiB，NPU 张量共 12GiB。
  同一进程内重复使用相同源和目标。
- 本页各次完成的 native 恢复均通过六个目的标记检查；本轮未开启全部描述符标记检查。
  这与 [上一轮](ASYNC-PATH.md)的全标记控制检查范围不同。

## 1. 软件资源环与设备队列同时观测

在已核验指令布局的运行库分配重试位置，读取资源环 head、tail、容量及最老任务 ID。
5ms CPU 时间采样发出 eventfd 通知，独立观察线程立即读取设备队列 head/tail，再读一次 head 检查稳定性。
信号处理器不调用 CANN 或驱动 API。

| 观察项 | 81 物理卡 5 | 91 物理卡 7 |
| --- | ---: | ---: |
| 预热后的六次恢复 | 0.364–0.575s | 5.563–11.951s |
| 同时有效的资源/队列样本 | 9 | 168 |
| 软件资源环满的样本 | 7 | 162 |
| 设备 head=tail 且重复 head 一致 | 7 | 164 |
| 采样至开始驱动查询的中位间隔 | 15.1µs | 20.2µs |

此前 20ms CPU 采样观察器的同类对照另有 14 次恢复：81 约 0.335–0.545s，
91 约 6.874–13.766s（均不含预热）。

这些计数是时间采样，不是独立事件数。它们证明忙等时资源状态的共现关系，不能单独证明资源回收错误。

## 2. 先用已知工作量标定队列读数

独立 C 程序在同一 stream 上提交 256 次 128MiB 搬运，再提交 512 个 256KiB 小块，
合计 32GiB+128MiB，最后同步并检查 512 个目的标记。
大块在底层进一步拆分；驱动跟踪实际成功接收 **1,024 条**队列项。

- 91 的全部驱动接收调用在约 **5.46ms** 内返回。
- 第一次随后观察到的设备队列为 head=0、tail=1；其后两者随搬运逐渐增长。
- 完成时 head=tail=1,024，墙钟约 **1.580s**，512 个标记通过。
- 相同负载、较轻的队列观察在 81/91 分别约 1.481s / 1.515s。
- 91 上不预加载观察器的控制为 1.591s，手动读取队列的控制为 1.354s。

因此，API 返回或驱动接收成功，不意味着全部逻辑任务已经进入被查询的设备队列。
中途 head=tail 也不意味着整个 stream 的逻辑工作已经完成。
初版 HAL 符号拦截器的一次标定未产出结果，原记录保留；后续版本在 SDK 初始化后解析查询符号，
不拦截队列查询/申请接口，并在上述独立程序上跑通。

## 3. 直接记录驱动接收时间

透明记录 `halSqTaskSend` 的进入、返回、SQ 位置、条目数、线程和返回码；
只将成功返回项计为已接收。两台机器各完成五次恢复，各有 **77,280 条**成功项，
与 5×15,456 个描述符一致；成功位置严格按 2,048 槽环顺序递增。
91 另有一次返回码 14 的调用，未计入接收数量。

按完成边界和位置递增展开环形索引，再将设备 head 位置关联到相应驱动接收记录：

| 节点与阶段 | 恢复时间 | 对齐样本数 | 相应 head 任务被驱动接收至观测的中位时间 | 最大时间 |
| --- | ---: | ---: | ---: | ---: |
| 81，stage-1 | 0.527s | 24 | 68.9ms | 71.9ms |
| 81，stage-3 | 0.530s | 22 | 69.3ms | 71.7ms |
| 91，stage-1 | 7.328s | 361 | 2,236.8ms | 3,930.7ms |
| 91，stage-3 | 6.230s | 307 | 2,274.0ms | 3,025.9ms |

这些时间包含前方任务的排队，不能当作单个 256KiB DMA 的执行时长。
91 的最大驻留样本中，设备 head=tail，驱动已接收但尚未推进完的推算数量为 2,047 条。
正常节点也存在类似数量的在途条目，但推进较快。
81 的第二阶段因较快而漏过一个整环；分析脚本依据已核验的 2,048 槽容量和成功提交数量展开，
在结果中明确记录修正次数。91 两个阶段均未使用这种补整环修正。

驱动接收接口本身最大调用耗时为 81 的 0.058ms、91 的 0.108ms。
所以，数秒驻留不能解释为这些接口一直没有返回。

公开驱动实现也区分软件发送尾和设备寄存器的 head/tail：
[队列实现，固定版本](https://github.com/hicann/driver/blob/471fa6b09b556cabdb7ed917a8dd2ec25ed0bc6b/src/ascend_hal/trs/core/trs_sqcq.c)。
这有助于解释标定现象；公开源码与已安装驱动没有建立逐函数二进制对应关系，
因此尚不能据此认定当前运行的一定是其中某个具体分支。

## 4. 观察器影响与在途数量控制

HAL 跟踪轮次交替关闭/开启设备队列轮询。81 四次约为 0.523、0.527、0.557、0.530s；
91 为 1.199、7.328、1.611、6.230s。
这两对提示观察可能放大慢节点的延迟，需要更多配对验证，不能把该轮差异全归结为应用负载。
另一方面，本轮 CPU 观察器的关闭设备轮询阶段也达到 5.563、9.586、8.369s，
先前轻量观察器和独立 CANN 对照同样出现严重慢化；队列轮询不是复现异常的必要条件。

进一步保持同一 stream、源和目标，分别每 512、128、32 个描述符同步，限制在途任务数。
81 的九次恢复全部完成：原始阶段约 0.435–0.564s，受控阶段约 0.502–0.580s，
没有显示明显性能改善。它只说明健康节点的控制路径能完成。
91 的对应探针在初始化期间遇到平台停止，尚无恢复结果，不能作为干预有效性证据。
早期同类有界提交的负结果仍见主报告，未被本轮替代。

## 5. 剩余的归因工作

1. 在原慢节点恢复后完成有界提交对照，并交替运行轻量与带队列观测的条件。
2. 核对两节点的驱动发送模式、固件运行状态和宿主机转发线程。
   仅修改容器 CPU affinity 不能控制容器之外的内核工作线程。
3. 用驱动/内核侧证据区分软件队列转发停顿与设备调度停顿。
   当前足以说明延迟在驱动接收之后，尚不足以唯一命名其中某个组件为根因。

91 在 21:45:11 被平台停止，记录的 initiator 为 `admin`。这个字段不证明人工操作或具体原因。
已完成数据均在停止前写入共享目录；中断探针原件与完成结果分开保留。
