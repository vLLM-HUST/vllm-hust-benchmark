# 原宿主机复现与设备任务时间线

本页接续 [IPC 与 stream 干预](FOLLOWUP.md)。本轮重新取得原宿主机，并加入第三台宿主机对照。 固定证据见
`raw/host-return-2010.tar.gz`；文件清单、大小和摘要见 `raw/host-return-2010-manifest.json`。逐次结果可由
`analysis/summarize_host_return.py` 从解包目录复算。 此证据包包含 11 组、98 次原生恢复，各组均正常完成；另外保留独立 CANN、CPU 同步及设备
profiling 控制。

后续的 [异步路径与控制实验](ASYNC-PATH.md)进一步关联接口与设备任务时间，补充 90 次原生恢复。 大空档对应的批次 API 已经返回，归因继续区分运行库、驱动和设备的推进过程。

## 当前结论

**本地恢复慢化存在系统性影响。已直接看到：数据搬运本身耗时接近，而任务之间的空档显著增多， 使总恢复时间变长。严重慢化与宿主机运行条件有关，同一卡、同一进程也会发生变化。**

主机侧任务申请、提交、完成查询和资源回收路径已有直接证据。底层哪个状态触发了这些空档， 目前仍未唯一确定。以下干预均作为诊断结果保存；其中没有一个在原宿主机上稳定消除了严重慢尾。

## 1. 资源与交叉对照

模型、连接器和 RDMA 不参与主要独立控制。所有卡由实机枚举确认为 Ascend 910B2。 原生恢复控制仍使用 96 个 K/V 平面、每平面 512 个位置、每位置 256KiB；每次恢复
161 块， 共 **4,051,697,664 bytes（3.773GiB）、15,456 个描述符**，每批最多 512 个描述符。 CPU 池 5GiB，NPU 缓冲区约
12GiB。各阶段复用同一组缓冲区、源数据和倒序目的位置。

| 工作区与阶段            | 宿主机           | 本轮相关物理卡 | 观察                                                 |
| ----------------------- | ---------------- | -------------- | ---------------------------------------------------- |
| 原 `hust-zsx`，前一快照 | host-192-168-0-2 | 2、7           | 已出现几十秒慢调用                                   |
| 重启后的 `hust-zsx`     | host-192-168-0-3 | 2、3           | 原生基线约 0.58–0.61s                                |
| `hust-zsx-91`           | host-192-168-0-2 | 2、7           | 同一宿主机 boot ID、同两张物理卡；新容器再次出现慢化 |
| `hust-zsx-81`           | host-192-168-0-4 | 4、7           | 继续作为较快的对照                                   |

重启后的 `hust-zsx` 实际被调度到了第三台宿主机，因此将它单独列出。随后停止该工作区， 恢复已有的 `hust-zsx-91`，取得原宿主机。91 的容器网络模式和 IPC_LOCK
权限与原容器不同， 慢现象仍可复现。原宿主机上的两张卡都出现过慢化，不能把问题归结为单张卡的固定性能。

这些对照支持宿主机条件相关性；它们未分离宿主机中的全部驱动状态、进程历史和物理路径因素。

## 2. 多 stream 在原宿主机上没有重现健康机器的收益

原宿主机的物理卡 7，先预热，再交叉测试同一原生恢复。

| 阶段         |  原始单 stream | 16 条 stream | 32 条 stream |
| ------------ | -------------: | -----------: | -----------: |
| 第一次出现   |         1.605s |       4.044s |       3.650s |
| 第二次出现   |         3.627s |       4.111s |       3.651s |
| 后续原始回访 | 2.561s、3.310s |            — |            — |

预热另为 12.256s。9 次恢复的目的标记检查均通过。 原始模式的位置按实际交叉顺序排列，表格各列不构成独立随机配对。 原始逐次顺序见摘要中的
`returned-native-stripe-device1`。

第三台宿主机上，原始阶段约 0.582–0.611s，16 条约 0.226–0.249s，32 条约 0.186–0.223s。 81 上的收益见
[前一轮完整模型对照](FOLLOWUP.md#6-%E5%AE%8C%E6%95%B4%E6%A8%A1%E5%9E%8B%E6%81%A2%E5%A4%8D)。 因此，多 stream
是部分运行条件下有效的实现方向，尚不能作为原宿主机严重慢化的通用修复。

## 3. 设备时间线：真正搬运只占一小段

### 3.1 同样 1GiB、16,384 个描述符的两宿主机控制

用 msprof 记录设备任务，只对实际记录数完整的阶段做定量比较。

| 宿主机、单 stream 阶段 |  总时间 | DMA 活跃时间并集 | 调用线程 CPU 时间 |
| ---------------------- | ------: | ---------------: | ----------------: |
| 原宿主机，第 1 次      |   799ms |            124ms |             707ms |
| 原宿主机，第 2 次      | 1,149ms |            128ms |           1,056ms |
| 81，第 1 次            |   430ms |            117ms |             381ms |
| 81，第 2 次            |   382ms |            114ms |             339ms |

原宿主机的数据搬运活跃时间只略长，总时间差额主要出现在搬运任务之间。 这组原宿主机的两个 16-stream 阶段只记录到各 8,200 个 memcpy 任务，少于预期 16,384； 其 DMA
时间不用于完整吞吐和空档结论。记录不完整不等于数据实际丢失。

### 3.2 原生 PegaFlow：同一进程内的快慢对照

通过公开的 `aclprofInit/CreateConfig/Start/Stop/Finalize` API，在原生子进程内采集设备任务； 各 API 成功状态保存在 native
日志。采集开始、结束边界和任务记录不完整的阶段单独标识。 以下两次均实际记录到全部 15,456 个 memcpy 任务。

| 原宿主机物理卡 7，同一进程 | stage-6 | stage-4 |
| -------------------------- | ------: | ------: |
| 原生恢复完成时间           |  1.435s |  4.414s |
| DMA 活跃时间并集           |  0.311s |  0.322s |
| 首个至最后一个 DMA 的跨度  |  1.432s |  4.397s |
| 任务间超过 1ms 的空档数    |       3 |     445 |
| 最大任务间空档             |  27.6ms | 148.4ms |
| 最后一个 DMA 到请求完成    |   1.3ms |   0.9ms |

后一个请求变慢，主要不是每次 DMA 搬运突然变慢，也不是数据早已搬完后统一通知晚了数秒； 更明显的变化是搬运任务在执行过程中被大量空档隔开。
设备时间线本身不能区分每个空档究竟由主机供给、设备调度还是完成回收链路引起， 需要结合任务申请满队列、CPU 栈和后续干预解释。

同尺寸独立 CANN 控制另外完成 12 次恢复，每次检查全部描述符对应的数据标记， 耗时约 0.36–1.51s；这轮未捕获超过 10s 的样本。它采用单一连续 NPU 分配， 不能当作与原生 96
平面 IPC 几何完全相同的替代实验。

采样器会改变执行时序。本轮原生 profiling 最慢约 4.41s，不能将其 DMA 活跃比例 直接外推到此前 48s 或 95s 的全部慢尾。

## 4. CPU 时间片与锁：哪些判断有依据

原宿主机后续原生恢复再次出现 **28.608s、34.787s、48.399s**。 这三次各自的 cgroup `throttled_usec` 增量均为 **0**。 例如 34.787s
那次，load 线程实际运行 CPU 约 30.17s，RT_RECYCLE 约 28.78s； 各自运行队列等待仅约 5.9ms、11.2ms。这是大量 CPU 执行伴随低任务推进效率，
没有看到容器用完 CPU 配额后被暂停几十秒的证据。

普通 CPU 对照包含同核、同 NUMA 异核、跨 NUMA 的信号量、互斥锁及读写锁。 每个条件重复 3 次，计数检查均通过。原宿主机和 81 的信号量往返、互斥锁中位数接近； 跨 NUMA
读写锁压力测试在两台机器上都较慢，原宿主机更慢。 这支持继续检查具体同步路径，尚不能据此认定真实恢复被读写锁阻塞。

早先 CPU 热点包含 mutex lock/unlock。增加计数后，原宿主机观察到约 **94,688,046 次解锁**， 其中观察到的带等待者解锁为
**0**。针对“带等待者解锁”的退避未实际触发。 这些热点主要说明代码频繁循环经过锁操作，不能把热点比例直接当作锁竞争时间。

## 5. 已执行的干预及其边界

| 干预                                        | 实际观察                                                                 | 判断                             |
| ------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------- |
| 针对带等待者的 mutex 解锁让步               | 原宿主机没有命中触发条件                                                 | 未形成有效干预检验               |
| 在任务申请重试的指定唤醒路径 yield / 短睡眠 | 指令布局校验通过，记录到数百万次重试及实际退避；后半段仍有 29–48s 慢调用 | 未稳定改善                       |
| FAST_SYNC / FAST_LAUNCH / 两者组合          | 首次 FAST_SYNC 为 0.822s，邻近原始为 17.567s、11.586s                    | 单次结果不足以归因               |
| 补齐预创建普通 stream 的匹配对照            | 同一进程交叉原始、预创建普通、FAST_SYNC；FAST_SYNC 未稳定胜出            | 首次差异不能作为已验证修复       |
| 每个目的描述符检查一个版本标记              | 9 次各 15,456 个目的标记全部正确，整批耗时约 0.81–1.78s                  | 有功能证据，未在本轮抓到严重慢尾 |
| 交叉改变 owner 检查活动和恢复前等待 250ms   | 等待组仍出现 18.610s，其他阶段未形成稳定关系                             | 尚未证明检查活动或短空闲可以修复 |

FAST_SYNC 的公开语义是主动查询完成状态；FAST_LAUNCH 在建 stream 时预申请资源。 参见
[CANN stream API](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta2/API/runtimeapi/aclcppdevg_03_0069.html)。
本轮保持 stream 优先级参数及 Linux 调度策略不变。

## 6. 对后续工作的影响

1. 恢复成本模型需要把字节搬运和小块任务推进分开；本轮尚不支持用一个统一的放大常数覆盖各宿主机。
1. 多 stream 的健康机器收益已验到原生恢复与模型请求，但部署前需覆盖慢宿主机、保存方向和并发语义。
1. 归因继续聚焦慢样本中的提交、完成与回收进度，补测具体读写锁或非阻塞锁等待。 CPU 配额、普通 CPU 性能、IPC 必要性等已做过有效对照，不再仅凭猜测重复。
1. 更底层的宿主机触发条件仍开放；未完成这一点前，不把“定位到了任务管理路径”写成唯一根因。
