# 驱动通道观测方法与正常节点标定

本页接续 [驱动接收与队列推进](QUEUES.md)，准备进一步区分驱动转发、设备执行和完成回收。 本轮在正常节点 81 完成两次独立 CANN
搬运和六次原生恢复；**尚未采到原慢节点的对应内核记录**。 因此，本页验证观测方法，不据此宣布异常的唯一触发原因。

原件为 `raw/kernel-view-2215.tar.gz`，61 个成员见同名 manifest。 复算脚本为 `analysis/analyze_kernel_view.py`，结果为
`analysis/kernel-view-summary.json`。 包内保留一次采集控制器在创建输出目录时失败的日志；该次尚未启动 NPU 程序。

## 1. 新增了什么观测

81 的容器没有可用的 debugfs 跟踪挂载，`perf_event_paranoid=4`，也没有内核跟踪所需的能力。 但可以只读访问 `/proc/trs_core` 和
`/proc/trs_chan`。

探针在创建 native 服务前记录已分配物理卡上的资源集合，再识别本次服务新增的上下文和通道。 仅采集该服务的进程摘要及新增通道，并记录每次读取的开始、结束时间：

- 通道累计转发条目数 `tx`；
- 驱动缓存的 SQ head/tail，以及单独显示的硬件 SQ head/tail；
- CQ 消费、分派、丢弃等计数，保留其原始含义；
- 模式、队列深度、IRQ、队列/通道 ID 和宿主机进程身份。

原生第一版只读进程摘要。虽然六个 stream/SQ 的 ID 都出现了，实际搬运的两个 SQ 却缺少详细字段。 第二版补读对应的独立通道，成功得到全部六个通道的状态。
后续分析必须采用有实际字段的通道数据，不能把摘要缺项解释成队列不存在或为空。

## 2. 独立搬运标定

使用 81 的逻辑卡 0 / 物理卡 5：同一 stream 先提交 32GiB 大块搬运，再提交 128MiB 小块。 底层共 1,024 条驱动任务。程序创建 stream 后有一次 3
秒就绪窗口，供外部采集器识别资源； 下表的搬运计时从窗口结束后开始。

| 条件                            | 搬运总时间 | 目的标记 |
| ------------------------------- | ---------: | -------: |
| 驱动发送跟踪 + 内核通道快照     |     1.472s |  512/512 |
| 再增加程序内 HAL head/tail 查询 |     1.464s |  512/512 |

这是单次配对，只验证两条观测路径能完成，不据此量化采样开销。 第二个程序中，最接近的两组内核/HAL 读取相隔约 3.6ms、5.0ms，进度相互一致： 例如内核读到
head=37、tail=138，约 3.6ms 前 HAL 为 head=36、tail=133。 约 5ms 前后的另一组分别为 head=177 / 179，tail 均为 1,024。
这为此前 HAL 读取的队列身份及进度含义提供了独立核对。

该实例的进程内核摘要显示 `uio_t`；驱动成功接收全部任务的跨度约为 5ms， 而硬件 tail 在更晚的快照中才达到 1,024。 这再次说明驱动接收计数与硬件已见任务数属于不同阶段。

## 3. 原生恢复验证

使用 81 的逻辑卡 1 / 物理卡 7，保持 161 块、3.773GiB、15,456 个描述符的原生 IPC 几何。 每次清零并检查全部 15,456 个目的标记；计时不含标记检查。
两轮各一次预热、一次关闭内核观测、一次开启内核观测。

| 探针                |   预热 | 关闭观测 | 开启观测 |  每次目的标记 |
| ------------------- | -----: | -------: | -------: | ------------: |
| v1，进程摘要        | 0.424s |   0.530s |   0.561s | 15,456/15,456 |
| v2，摘要 + 独立通道 | 0.481s |   0.535s |   0.567s | 15,456/15,456 |

v2 的 pending 快照读取约 3.45ms；完成后的快照约 3.46ms，后者在计时终点之后。 读取过程不是原子的，分析时要使用各通道自己的时间边界。

v2 的 load 通道在 pending 快照中累计转发 33,501 条，硬件 head=732、tail=733， 说明这一次读取时硬件只剩约一条在途任务。完成时累计转发 46,368
条，即三次恢复的全部描述符， 硬件 head=tail=1,312，符合 46,368 对 2,048 槽环取模。 正常节点也可能呈现硬件队列浅、软件尚有任务的状态；需要结合推进速率与驻留时长解释。

## 4. 宿主机发送机制的线索

81 两张已分配卡的发送 workqueue 都可读：unbound、nice=-20、max_active=1，CPU 掩码覆盖全部 CPU。 共享 worker pool ID
不能直接解释成两个队列由同一条线程串行执行。 两宿主机已经记录的固件标称版本均为 9.0.0.0.205，未观察到标称版本差异。

公开驱动源码包含独立的软件队列转发线程、触发 workqueue 及逐条转发逻辑：
[固定版本的实现](https://github.com/hicann/driver/blob/471fa6b09b556cabdb7ed917a8dd2ec25ed0bc6b/src/sdk_driver/trsdrv/trs/trs_core/trs_hw_sqcq.c)。
这支持将宿主机发送线程和 IRQ 纳入下一步调查；当前没有建立该源码与安装模块的逐函数对应关系， 更没有测得慢节点中具体哪个线程失去运行机会，不能据此认定线程调度就是根因。

## 5. 慢节点恢复后的判别标准

下一轮保持轻量 API/驱动发送跟踪，交替开启内核快照；避免同时开启高频 HAL 队列轮询。 复用 `restore_causal_probe_kernel_20261110_v3.py`：v2
的通道读取已经验证， v3 在此基础上准备了同时间窗的宿主机 CPU、调度及相关 IRQ 计数，**v3 尚未执行**。

| 慢窗口中的证据                             | 下一步重点                                     |
| ------------------------------------------ | ---------------------------------------------- |
| 驱动已接收数持续领先通道转发数，硬件队列浅 | 驱动软件队列转发、宿主机 worker 与唤醒         |
| 转发数已经追上，硬件 head 明显落后 tail    | 设备任务调度、DMA 及设备内竞争                 |
| 硬件完成进度追上，但请求仍未 ready         | CQ、运行库回收及完成通知                       |
| 快照未覆盖停顿                             | 补充事件触发采集，不用未覆盖的快照排除候选原因 |

91 自 21:45 的平台停止后尚未恢复，本轮对应慢节点采集仍待执行。
