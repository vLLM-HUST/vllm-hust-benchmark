# 保存方向的多 stream 对照

本次补齐 NPU→CPU 保存方向，接续 [恢复方向与任务队列干预](FOLLOWUP.md)。 原机器曾在保存阶段超时，因此后续严重慢尾复测必须覆盖这个方向。

## 设计

- 宿主机 81，逻辑设备 1 / 物理设备 7，Ascend 910B2；CANN 9.1.0。
- 使用同一组 96 个 IPC 导入的 NPU 平面，每次保存 161 个块，共 3.773GiB、15,456 个描述符。
- CPU 池 24GiB，五组内容共约 18.87GiB；各阶段使用独立哈希和不同数据标记，触发真实保存。
- 顺序为：原始预热、原始、D2H 16 条 stream、原始、D2H 32 条 stream。
- 每次保存达到完整前缀可见后，按原始 H2D 路径恢复到另外的目的块，检查当前阶段的六个数据标记。
- 仅此有限对照在 81 上运行。私有 v2 拦截库增加 D2H 模式；其余连接器与缓存语义沿用现有路径。

## 结果

| 计量顺序 | D2H stream 组织 | RPC 保存确认 | 完整前缀可见 | CANN batch 累计 | CANN sync 累计 |
| -------- | --------------- | -----------: | -----------: | --------------: | -------------: |
| 1        | 原始            |       0.804s |       0.805s |          0.665s |         0.103s |
| 2        | 16 条           |       0.639s |       0.640s |          0.084s |         0.499s |
| 3        | 原始            |       0.784s |       0.785s |          0.649s |         0.102s |
| 4        | 32 条           |       0.644s |       0.645s |          0.079s |         0.510s |

预热完整前缀可见为 0.843s。全部五次保存与随后恢复检查成功，标记对应各自的新版本。 这里的 sync 是对该阶段实际涉及的所有 stream 的同步调用累计时间。

原始 batch 调用约 0.65s，其中调用线程 CPU 也约 0.65s。多 stream 的 batch 调用约 0.08s， 调用线程 CPU 同样约 0.08s；同步调用中的 CPU 另约
0.05–0.06s。 这些数字说明提交方的活跃等待显著减少，但部分等待转移到了最后同步，**总保存时间只从约 0.79s 降到 0.64s，不能把提交阶段的倍数直接当作总收益。**

这一结果补齐了保存方向的功能与性能对照。它仍未回答原机器为何会出现几十秒的停顿； 需要在原宿主机重复相同干预并观察回收线程。
