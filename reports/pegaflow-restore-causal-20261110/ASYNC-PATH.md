# 已下发任务的异步推进与控制实验

本页接续 [原宿主机设备时间线](HOST-RETURN.md)。追加证据包含 **18 组、90 次原生恢复**，
各组正常完成，另有 8 次带版本标记的独立 CANN 搬运控制。
原件为 `raw/async-path-2100.tar.gz`，清单为 `raw/async-path-2100-manifest.json`；
原生逐次结果和计数可由 `analysis/summarize_host_return.py` 复算。

## 1. 对空档的位置有了更准确的判断

前一快照中，原生恢复同样的 3.773GiB，从 1.435s 变为 4.414s，主要伴随设备任务之间的空档增加。
本轮进一步将设备 CSV 与 msprof 数据库的任务记录逐项匹配，再按 connectionId 关联批次 API。

- 设备 CSV 的 138,334 条 memcpy 记录全部匹配；纳入定量对照的两个请求各有完整 15,456 条记录。
- profiler 记录的 279 次批次 API，与独立拦截器的 279 次调用对应；开始、结束时间最大差约 0.50ms。
- 4.414s 请求中，445 个超过 1ms 的空档合计约 **2.572s**。
  每个空档的下一任务所属批次，API 均已在空档开始前至少 **12.25ms** 返回。
- 最大空档为 148.43ms；对应批次 API 在该空档开始前 **162.74ms** 已返回。

因此，这些空档不能简单解释为调用方还没有提交对应批次。
已有数据将范围进一步收敛到 **接口返回之后的运行库、驱动和设备任务推进过程**。
接口返回不等同于已经写入硬件队列，现有 API 时间线尚不能在这三层之间唯一定位。
CPU 反复申请任务资源、唤醒回收的现象，也可能包含下游推进慢造成的背压。

上述关联只采用任务记录完整的阶段；边界和不完整阶段保留原数据。
复算脚本 `analysis/analyze_submission_gaps.py` 使用只读 SQLite 连接，先检查 CSV/数据库一致性，
再输出 `analysis/submission-gap-summary.json`。这组证据来自前一固定包的原生 profiling，
不把它直接外推为此前 48s、95s 慢调用的完整设备时间分解。

## 2. 保持相同小块，改变接口

原宿主机仍为 host-192-168-0-2，逻辑设备 0/1 对应物理卡 2/7。
交叉顺序均为原始批量异步、逐块同步、原始批量异步、逐块同步。
每次恢复前清零所有目的块的标记，完成后检查每个描述符的目的标记。

| 物理卡、恢复量 | 原始异步两次 | 逐块同步两次 | 每次检查数 |
| --- | --- | --- | ---: |
| 卡 7，1.5GiB | 4.341s、4.817s | 1.137s、1.273s | 6,144 |
| 卡 2，3.773GiB | 0.494s、0.545s | 1.142s、1.074s | 15,456 |
| 卡 7，3.773GiB | 3.190s、4.164s | 2.422s、2.005s | 15,456 |

全部目的标记检查通过。同步方式保留小块数量、来源及目标映射，绕开异步提交后的排队/回收方式，
在较慢阶段有所改善；在较快阶段反而更慢。它是有用的路径对照，尚不是通用性能修复。
同步方式还增加了阻塞、限制了在途任务量，不能仅凭这张表认定某个底层函数有缺陷。

随后保持异步语义，改为对各小块分别调用 `aclrtMemcpyAsync`，最后再统一同步：

| 物理卡，3.773GiB | 原始批量异步两次 | 逐块异步两次 |
| --- | --- | --- |
| 卡 7 | 1.298s、3.743s | 1.269s、1.526s |
| 卡 2 | 1.288s、1.552s | 0.714s、20.716s |

逐块异步也出现严重慢化，说明 `aclrtMemcpyBatchAsync` 不是出现慢尾的必要条件。
这组检查同样覆盖每次的全部 15,456 个目的标记。

## 3. 减少任务数量，同时计入 CPU 重排成本

独立 CANN 控制保持 1GiB 数据、同一源数据和目的布局，CPU 重排后由 16,384 个小块变为 64 个大块。
每轮更新源标记，完成后读取目的数据并检查全部 16,384 个标记，防止前一轮结果掩盖未写入。

- 原始四次总时间：0.921s、0.757s、5.366s、1.511s。
- 整理后四次总时间：0.856s、0.634s、0.630s、0.886s；均已计入 CPU 整理时间。

原生路径进一步保持 3.773GiB，收集本次所有描述符，按目的位置排序，CPU 整理后提交 96 段连续区间。
7 次恢复（含原始预热）的全部 15,456 个目的标记均通过。

| 顺序 | 原始模式 | CPU 整理模式 |
| --- | ---: | ---: |
| 第一对 | 2.372s | 6.729s，包含首次注册暂存区约 4.670s |
| 第二对 | 1.528s | 2.380s |
| 第三对 | 6.851s | 2.810s |

后两次整理本身分别约 0.964s、1.277s，提交后同步分别约 1.399s、1.513s。
减少任务数可以缓解部分慢调用，但它也引入 CPU 搬运，并且少任务下仍存在明显等待。
这些结果不支持把全部异常都解释为“描述符数量太多”，也不支持直接采用这一原型替换生产路径。

原型延迟到最终 stream 同步时才真正提交整理后的数据，适用本轮固定、无重叠写的控制。
生产化需要另外处理并发、源数据生命周期、失败索引、暂存内存额度和清理。

## 4. CPU 与内存放置的交叉实验

固定 NPU，固定所有 native 线程的 CPU NUMA 节点，改变进程内存节点。
每个配置建立两个独立进程，每个进程预热后测两次。实际 affinity 和 `numa_maps` 均留档，
约 5GiB 池及大块 heap 的页落在指定节点。

| 物理卡；固定 CPU 节点 | 内存节点 | 第一个进程两次 | 第二个进程两次 |
| --- | ---: | --- | --- |
| 卡 2；CPU 6 | 6 | 2.009s、10.397s | 8.220s、1.526s |
| 卡 2；CPU 6 | 2 | 2.963s、2.931s | 9.302s、2.163s |
| 卡 7；CPU 2 | 2 | 1.500s、1.858s | 1.499s、2.205s |
| 卡 7；CPU 2 | 6 | 27.707s、45.688s | 1.229s、1.373s |

内存节点会改变运行条件，但相同配置重建进程后仍可相差一个数量级。
当前结果不能用单一的本地/远端内存标签预测慢化。
这里改变的是进程默认内存策略，CPU 缓存池与运行库 heap 一起变化，不能把结果只归因于 KV 源内存。

另一个同进程交叉控制依次使用单核、全部 CPU、两核、全部 CPU、本地 NUMA、全部 CPU、单核、全部 CPU。
8 次约 1.185–3.056s，没有形成稳定的优劣关系，也没有在该轮捕获几十秒慢尾。

## 5. 拓扑发现中另一个可修复的问题

实际 `npu-smi info -m` 报告：物理卡 2 的逻辑 ID 为 0，物理卡 7 的逻辑 ID 为 1；
拓扑表报告其 CPU 范围分别为 144–167、48–71。
原生日志却记录 `Device 0 -> UNKNOWN`、`Device 1 -> UNKNOWN`，GPU worker 也使用 UNKNOWN。

检查 [numa.rs 的固定源码版本](https://github.com/vLLM-HUST/pegaflow-hust/blob/1fbf0f2fe73b766db7d2c58a5819798ef17a1ea1/pegaflow-common/src/numa.rs)：
未设置可见设备变量时，`get_npu_numa_affinity` 取得设备数量后遍历 `0..count`，
将这些逻辑序号传给按物理编号查拓扑的函数。这个容器的物理编号是 2、7，不能由数量推导为 0、1。
本轮 probe 显式清除了 `ASCEND_RT_VISIBLE_DEVICES`，使这条发现路径的局限直接暴露出来。

该源码版本是本轮检查对象；运行二进制身份仍以前页记录的二进制摘要为准。
后续应从实际逻辑/物理映射发现拓扑，避免 UNKNOWN 导致预期绑核失效。
这一问题有独立的代码与运行日志证据，但手动固定 CPU/内存后仍能复现慢化，因此还不能作为全部慢尾的根因。

## 6. 锁与额外让步

读写锁拦截覆盖的批次记录共有 927,980 次读锁调用、0 次写锁调用；
905 个采样读锁等待最长约 610ns，未记录到超过 250µs 的读写锁等待。
同期原生恢复仍出现 8.891s、10.080s、18.639s 等慢调用。
这降低了“真实读写锁长时间阻塞”作为该轮直接原因的可能性，采样不覆盖每一次读锁等待。

唤醒路径中每 64 次重试额外让步的交叉控制，原始约 1.820–1.875s，干预约 1.537–1.855s。
本轮未形成严重慢基线，也没有证明它能修复严重慢尾。

## 7. 下一项决定性观测

已通过当前 SDK 的 HAL 只读查询取得设备 SQ head/tail；本轮得到 4,620 个快照，两项查询均返回成功。
SQ depth 查询返回 17，故这些数据不用于计算占用百分比或断言满队列。
9 次恢复约 1.316–3.021s；本轮也没有捕获几十秒样本。

下一项观测将对齐两种进度：

1. 主机 runtime 任务资源池的 head/tail，带具体采样时间和已核对的对象布局。
2. 对应设备 SQ 的 head/tail，并用 stream ID 映射确认是同一条恢复路径。

同时交叉开关额外的 HAL 查询，检查观察器是否改变执行时序。
只有取得这些证据后，才进一步区分设备未完成、驱动未推进和主机未及时回收。
当前已确认的异步推进慢化、拓扑缺陷、各项干预的效果范围分别记录，继续保留底层触发原因的开放状态。
