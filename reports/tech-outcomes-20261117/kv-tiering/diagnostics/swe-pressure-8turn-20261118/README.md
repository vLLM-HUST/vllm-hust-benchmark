## 实际恢复、少算prefill与性能边界

本次MOD实际H2D累计33.472512 GB、D2H60.207104 GB，外部前缀命中1093632
token；Native外部命中为0。实际计算prefill从7137055降至5588767，减少1548288 token（21.6937%）。其中外部恢复1093632
token，local_cache_hit由266240增至720896，另增加454656 token；不能把全部prefill节省都归因于外部读取。

FS累计逻辑读取125.478994 GB、写入68.701553 GB，观测到2957个load
hits。重复读会让累计读取量超过容量，FS读字节也不能等同于最终恢复至HBM的字节或物理磁盘流量。缺少无FS候选对照，本次不能独立量化FS贡献，也不能将+17.63%全归因于文件层。

新引擎在正式生成前的部分分层指标尚未注册，原快照中相应before/delta保留null，只列after累计观测值，不用0伪造基线。第000轮结束这些传输计数均为0；后续已注册轮次可直接求差。完整before/after见[numeric/](numeric/)，离线检查保留标签并区分counter和gauge。

## FS配额耗尽与后台错误，不能省略

虽然2032条推理请求全部成功，但MOD文件层在后半段耗尽64 GiB配额，日志出现 `FS segment quota exhausted`。最终累计：

| FS计数                 |  末值 |
| ---------------------- | ----: |
| capacity_rejections    |  4206 |
| store_errors           |  2148 |
| load_errors            |    27 |
| queue_rejections       |    72 |
| checksum_errors        |     0 |
| gc_segments / gc_bytes | 0 / 0 |

这些分别是作业、队列或分配尝试计数，不能相加充当失败请求数。公开[错误类别导出](numeric/server-error-categories.json)保留2103条quota-exhausted日志的类别计数和原日志哈希；其数量与Prometheus作业计数口径不同。HTTP成功没有覆盖掉后台错误；checksum_errors=0也不是KV逐字节正确性验证。

上述吞吐已包含配额耗尽阶段，不能扣除错误耗时“修正”成绩。此组证明有外部恢复、FS读取及该配置下的总体净收益，**不是无错误的三层容量验收**。负载、并发、graph/eager和输出规则与原五项同时变化，不构成对每项配置独立贡献的因果隔离；固定顺序、单次配对也不构成稳定性确认或任务成功率结论。
