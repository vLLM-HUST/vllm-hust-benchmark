# 离线批量实验契约

此文件依据用户2026-10-17最新纠正，覆盖其他文档中把客户端固定并发或并发扫描作为当前主实验默认值的表述。历史结果保留其原协议，不改写成离线结果。

## 目标与输入场景

目标：验证 request-throttling-controller 在离线批量、多轮 Agent 轨迹同时竞争 KV 时，能否通过 program 准入、暂停/恢复及缓存复用提高整体执行效率。

整批 N 个 program 在时间0同时到达，客户端不设并发上限。每个 program 内部仍按原轨迹依次执行模型调用、工具等待和后续调用；不能把存在依赖的所有后续调用一次性并行发送。

这里的“无并发上限”指没有客户端限流，实际批次仍有明确大小 N。后端的实际执行数由 Controller 与引擎根据资源决定；等待、暂停和恢复都是要验证的系统行为。

## 必须分开记录的维度

| 维度           | 当前离线协议                                                   |
| -------------- | -------------------------------------------------------------- |
| 到达方式       | 整批在时间0到达                                                |
| 批次大小       | 固定 N，记录完整输入/轮数与 SHA256                             |
| 客户端并发限制 | 无；不是调参或扫描变量                                         |
| program 内依赖 | 保留原始轮次、输入/输出长度和工具等待                          |
| 后端限制       | 记录实际 max_num_seqs、batch tokens、KV 配置；不当作客户端限制 |
| 对照           | 同输入、同模型配置、同传输路径，Controller 调度关闭/开启       |
| 观测           | 实际执行数、等待/暂停、KV 使用、抢占、缓存命中、吞吐及错误     |

固定并发2/4/32的闭环回放属于另一种负载场景，不能替代本协议。“最强基线”也不意味着默认先扫描客户端并发。只有用户明确要求限并发/在线实验或指定 ThunderAgent
历史复现时，才另建场景和协议。

## 复用已有回放器

`experiments/workload/replay_sessions.py` 的 `--concurrency 0` 使用原始到达时间，为每个 program
建立独立执行线程，不用固定数量的客户端 slot。离线批量还必须验证 CSV 中的 arrival_time 全为0；单有参数0并不能证明同时到达。

`experiments/workload/run_throttle_window_trial.py --plan <plan.json>` 的当前离线计划显式配置：

```json
{"arrival_mode":"offline-burst","concurrency":0,"client_concurrency_limit":null}
```

`0` 是已有回放器表示不设客户端 slot 上限的接口值，不表示没有请求。程序数由完整输入决定。执行仍通过已有 RIDE/具名 Ray Jobs；不另起模型或改写官方调度核心。

## 短验证与证据边界

先用尽量短的窗口验证容量压力、调度动作与实际收益；窗口两侧采用相同时间边界和计量定义。记录窗口内完成调用、输出吞吐、完整完成 program 数、错误及未完成情况。窗口结束的主动取消单列。

完整批次耗时必须等该批所有 program 完成并通过
token/历史/输入一致性检查后才能报告。窗口吞吐提升不能写成完整批次耗时下降。没有触发或不符合预期立即诊断，不通过搜索客户端并发来改变用户给定的离线到达场景。
