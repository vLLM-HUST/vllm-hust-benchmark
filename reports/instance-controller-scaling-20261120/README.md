# RIDE Instance Controller RTX A6000 扩缩容实测

## 1. 结论

- 单峰两组各成功 6,870 条。固定组 → 动态组的 P95 为 449.89 → 344.56 秒，相对变化 -23.4%。动态组未通过联合门槛。
- 双峰两组各成功 10,050 条。固定组 → 动态组的 P95 为 398.55 → 399.78 秒，相对变化 +0.3%。动态组未通过联合门槛。

## 2. 系统与改动

四张 RTX A6000 运行 Qwen2.5-7B-Instruct，每张卡一个模型副本。RIDE 0.3.6 管理生命周期，Instance Controller 0.1.12.dev3
控制副本启停和排空，Ray 执行作业。客户端经路由器访问 vLLM 0.30.1rc1.dev535+gd2125ea68。模型使用 BFloat16，初始副本及接过业务流量的扩容副本均有原生
CUDA Graph 捕获记录。

## 3. 配对条件

每个场景两组使用相同设备、同一份 Azure Code 请求轨迹、相同输出长度预算和相同预热。从两个已就绪副本开始，先动态后固定。业务请求无超时、无并发上限，并逐条匹配请求身份、到达偏移和输入输出
token 数。

单峰窗口 1,180 秒，第 840 秒起以 19 请求/秒持续 180 秒。双峰窗口 2,000 秒，第 530 秒起以 19 请求/秒持续 90 秒，第 1,700 秒起以 27 请求/秒持续
100 秒。

## 4. 端到端结果

## 5. 峰内接单与扩容策略

- 单峰第 1 峰有 3 个副本实际接单。
- 双峰第 1 峰有 2 个副本实际接单。82 次观测中有 82 次因预算不足未启动额外副本。峰内首次限制时有 171.53 卡秒，额外启动需要 230 卡秒。
- 双峰第 2 峰有 2 个副本实际接单。89 次观测中有 89 次因预算不足未启动额外副本。峰内首次限制时有 -121.99 卡秒，额外启动需要 230 卡秒。

单峰第三个副本在第 674.8 秒启动，第 957.8 秒收到第一条转发请求，间隔 283.0 秒。 双峰第三个副本在第 1171.8 秒启动，第 1453.3 秒收到第一条转发请求，间隔 281.5
秒。

## 6. 模型预约与平台开销

模型预约从 Ray 模型作业启动计至终态或对应观测边界，包含加载和等待就绪。四张物理卡始终由 Coder 工作区预留。每组窗口内的平台资源分别为单峰 4,720 卡秒、双峰 8,000
卡秒。模型预约与平台预约使用不同分母。

## 7. 验收门槛与适用范围

预设联合门槛要求窗口内平均预约至多两个模型副本，且动态组 P95 不高于固定组的 105%。每个工况只有一对运行，覆盖本次模型、GPU 环境和两份负载。语义任务准确率、设备算力利用率和实际计费未测。

## 8. 复算依据

复算输入为逐请求终态、Ray 作业时间及路由和控制器事件。发布摘要保留复算工件的摘要，原始请求文本和平台内部身份由实验归档保管。
