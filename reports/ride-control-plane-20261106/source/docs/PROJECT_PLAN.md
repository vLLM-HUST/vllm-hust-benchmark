# RIDE 项目中长期规划

负责人：毛言粲（myc）。执行开发者：当前开发代理。版本：2026-11-06，第二版。

用户本次决定：一项一项研究、逐步击破，后续持续按本计划推进。本文规定长期目标、研究顺序与阶段出口；[统一路线图](architecture/CONTROLLER_ROADMAP.md)是唯一任务状态；[系统设计](architecture/INDEPENDENT_CONTROLLERS.md)规定接口与职责；[效果验证契约](architecture/CONTROLLER_EVALUATION.md)规定当前测量方法。本文不复制每轮结果。

## 1. 长期目标与完整范围

**建设可复用的多机推理运行时控制面：各Controller独立开发和运行，先逐项证明其有效场景与代价，再证明必要的协同能优于独立策略组合。**

工程目标：Controller独立Git仓库、独立Python包、独立进程，只依赖公共RIDE SDK，通过版本化API协作；RIDE提供安装、生命周期、执行适配、模型管理与观测，Ray提供分布式执行。业务仍为客户端→限流层→模型；RIDE不代理每次推理，也不替代云平台。

效果目标：交付经过真实模型验证的组件，说明相对哪个基线、在哪个负载区间、改善哪项指标、增加什么代价、何时无收益。组件数、接口数、测试数和模型启动成功不能代替效果。

研究目标：在已可靠运行的组件之间寻找可复现的冲突，研究状态与工作流信息能否改善跨模块决策。上游迁移和统一API不自动构成算法创新；不承诺正收益或论文录用。

完整范围沿用[2026—2027飞书布局](https://ocnkis1vvvv6.feishu.cn/wiki/CuerwjP5jiy2yNkHYdgcjoC6nRc)：Request/Program、KV、资源与副本、引擎配置与prefill/decode组织、模型与LoRA、并行拓扑、工作流与SLO、跨模块协调。近期先完成Request＋KV＋资源，不能把近期路径当作永久缩减范围。

## 2. 未来三至六个月：按顺序完成四项研究

周期是具备必要环境和协作条件时的有效工作量估算，非承诺日期；资源等待与外部适配单独记账。每次只激活一项策略研究；必要的故障修复和公共测量服务于该项，不另开一轮无明确消费者的基础设施建设。其他聊天的独立研究不由本计划接管。

| 顺序 | 研究问题与预计投入 | 可交付结果 | 进入下一项的条件 |
|---|---|---|---|
| 前置资格，约3–5个工作日 | 新版协议在真实Ray/模型上是否正确？此前工作量为何不匹配？ | 少量完整多轮、实际扩缩/双排空/停止/恢复；容量、启动、工作量核验脚本 | 正确性与测量链通过；失败先修首个失败层，不跑长性能扫描 |
| 第一项：Instance，约3–4周 | 何时值得扩容？何时缩容能省资源且不伤害服务？ | 一个有来源的工作量感知扩缩策略及收益/边界报告 | 独立验证得到有效场景，或有可复核的无收益结论并决定保留基线 |
| 第二项：缓存感知路由，约2–4周 | 缓存复用与负载均衡如何取舍？ | 可独立开关的策略；真实缓存/重算与任务时延证据 | 完成强基线、独立验证、边界或负结果判读 |
| 第三项：KV，约3–6周 | 多轮等待或缩容时，保留/恢复何时比重算划算？ | 一个真实后端的状态保留/恢复闭环、成本交叉点和容量竞争对照 | 数据和输出正确、动作有回执，再完成效果或负结果判读；后端不支持不能标完成 |
| 第四项：协同，约4–6周 | 独立策略是否冲突？协调是否优于它们各自工作？ | 一个由证据驱动的协调机制、强组合基线、消融和故障/成本报告 | 验证相对独立组合的增量，或结束该假设；据证据决定论文范围 |

### 第一项：Instance Controller

收益场景：持续增长、长突发与重复突发。一次只移动突发持续时间或间隔；加入短于冷启动的突发作为可能无收益场景。到达时间预先冻结，不等新模型Ready才发送业务。

先测单副本不同输入/输出长度的容量、真实启动/Ready时间及控制开销，再选择一个成熟策略。来源候选为[Dynamo Planner](https://docs.nvidia.com/dynamo/dev/reference/components/planner-configuration)与[llm-d扩缩指南](https://github.com/llm-d/llm-d/blob/main/guides/workload-autoscaling/README.md)的负载/饱和度信号。实施前固定代码版本与实际算法，不把开发文档当稳定实现，不搬整套平台。

必需对照：固定1副本、固定最大副本、当前按请求数量且有合理延迟的策略、选定的成熟工作量感知策略。自行改进时上游策略独立保留为基线。只改变扩缩决策，其余限流/缓存/路由保持共同配置。

完成判据：相同服务质量下减少真实设备预约，或相同资源约束下改善完整任务完成与长尾。不能用多卡击败少卡证明算法有效，不能把集群内预约释放叫平台省钱。

### 第二项：缓存感知路由

收益场景：多个实例承接共享长文档、公共前缀和多轮任务。先固定副本数，隔离路由收益；再移动前缀共享比例和热点程度。没有复用的输入是必要边界。

来源候选：[AIBrix前缀缓存与负载联合选择](https://aibrix.readthedocs.io/latest/features/gateway-routing/prefix-cache-aware-routing.html)及[会话亲和](https://aibrix.readthedocs.io/latest/features/gateway-routing/agentic-routing.html)。必需对照为轮询、最少负载、会话亲和、成熟的缓存与负载联合策略；不能仅赢轮询就宣称有效。已有任务状态绑定保持；只路由新任务不冒充运行中迁移。

核验真实引擎缓存、命中token、prefill重算、首token时间及完整任务时间。路由器“曾经发往此处”的缓存估计与引擎真实命中分列；实际tokenizer/模板/缓存语义不等价时先停性能比较。独立Controller与数据路径适配的责任在阶段设计中明确，保持独立仓库边界，不默认改ThunderAgent核心。

### 第三项：KV Controller

收益场景：长上下文任务进入工具等待，其他任务争用容量；或缩容前需要保留状态。先固定副本与路由，完成单一后端的数据资格，再测容量竞争。

优先复用已有可支持后端；[Mooncake](https://www.usenix.org/conference/fast25/presentation/qin)提供状态存储/调度的相关机制，[LMCache控制接口](https://docs.lmcache.ai/kv_cache_management/controller.html)提供查询、保留、移动和完成检查的适配参考，不强制同时接入。只读lookup、CPU mock或copy=false不能抵真实数据动作；外部存储保留不等于引擎显存已经释放。

先核字节/状态覆盖、真实续轮输出继承、目标可用和源释放边界；当前混合模型必须覆盖Attention与循环状态，旧full-attention资格不外推。随后比较原生缓存、后端默认淘汰/恢复策略、选定简单保留策略；计入传输、加载、占用及对其他请求的干扰。先测何时比冷重算划算，再考虑复杂算法。

### 第四项：独立Controller协同

只在出现明确冲突后选题，例如Instance准备缩容，但该实例仍有高价值多轮状态。先用原始事件证明独立策略的代价，再决定保留副本、迁移状态或重算恢复。

相关强基线包括[Llumnix运行时重调度](https://www.usenix.org/conference/osdi24/presentation/sun-biao)、成熟路由/扩缩/缓存方案及其合理组合。至少比较单项策略、独立组合、候选协调和去掉关键观测/决策的消融。实际可比性、必要适配和无法运行项事前说明，不省略会改变结论的强基线。

只有更好使用任务阶段或状态价值带来独立增量时，才讨论研究贡献。不预设通用全局事务、任意故障恢复或自动最优策略；外部动作未知时保留阻塞和原件，不用盲目重试制造成功。

## 3. 六至十二个月：逐项补齐完整控制面

四项研究得到可复用结论后，按实际需求一次选择一个后续控制域，不提前同时开工：

| 控制域 | 启动条件 | 最小验收对象 |
|---|---|---|
| 引擎配置与prefill/decode组织 | 实测存在prefill/decode干扰或配置失配 | 一个配置轴或P/D组合，真实切换成本与服务质量对照 |
| 模型驻留与LoRA | 真实多模型/adapter负载存在驻留或冷启动瓶颈 | 一个模型/adapter策略，计入加载、挤出与质量约束 |
| 并行拓扑 | 固定布局失配且具备底层适配协作条件 | 一个固定模型、一个TP/PP等轴；先验重建/实例切换，不承诺任意在线重分片 |
| 工作流与SLO | 任务依赖与完成目标可核验 | 一个工作流策略，相对成熟请求/任务策略的增量，不用未来工具结果 |
| 跨域协调与外部复用 | 多模块实际冲突或外部使用者出现 | 一个外部独立策略仓库接入、兼容/故障验收与效果 |

每项继承相同来源、基线、正确性、效果与失败处理要求。增加控制域不等于建设新平台；公共层只加入实际消费者需要的稳定能力。

## 4. 每项研究统一怎么验收

顺序固定：问题与场景→上游版本/许可证/来源与差异→强基线→软件负例→真实小闭环→匹配发现→独立重复与留出→边界和归档。沿现有[效果契约](architecture/CONTROLLER_EVALUATION.md)与[控制面SOP](https://ocnkis1vvvv6.feishu.cn/docx/N9pzdG7d2ojuyAxV7jhcud8VnBg)执行。

预期目标与已有证据分开：组件/协同的初步研究目标为同约束下有效吞吐改善至少5%，或同服务质量约束下真实设备预约秒减少至少10%。这些沿用总蓝图的候选目标，**不是收益预测，也不是所有组件通用的已冻结门槛**。路由/KV可选择完整任务时延或prefill工作量等合适主指标；首次正式对照前记录最小有意义差异与质量/长尾/公平性约束，执行后不降门槛。旧Request/B1独立冻结标准不由本文覆盖。

至少三组新鲜交替配对，加未用于调参的留出输入；报告每组、波动与统计不确定性。三组只是最低起点，无法区分噪声则结论待定。实际输出及续轮输入工作量必须核验，固定max_tokens不代表同工作量；受控服务轨迹只证明该轨迹结论，最终还需完整多轮反馈验证。输出或质量变化不能静默忽略。

每项交付五件东西：独立可安装版本及来源差异；可复现配置/脚本；原始数据与SHA；收益及全部失败/负结果报告；有效与无效区间。工程正确性、策略实际生效、收益分别核销。

阶段判读：继续并保留已验证范围；缩小问题/采用强基线并结束该候选；缺外部能力时明确依赖与解除条件。最后一种可由负责人决定转到下一项可独立问题，原任务仍未完成；不能把阻塞、未运行或不可比较写成无收益。连续两次同因失败先复核前提，不盲扫。

## 5. 每周怎样follow

每周只复核同一张[统一路线图](architecture/CONTROLLER_ROADMAP.md)，不另建第二份状态表。开发者报告，负责人据证据决定范围：

1. 当前唯一活动研究问题是什么？本周要证伪什么？
2. 完成了哪个真实动作或完整对照？原件在哪里？
3. 相对哪个基线，什么变好、什么变坏、开销与未知是什么？
4. 阶段出口是否满足？继续、收窄、结束候选还是需要外部协作？
5. 下周唯一可核验交付物是什么？依赖和资源边界是什么？

每阶段结束完整复盘。源码、输入、基线或门槛改变先记录原因，新实验用新run，不回写历史。没有稳定收益可交付否定结论；没有真实证据则保持未完成。本计划不创建定时通知或自动化任务。

## 6. 当前起点与立即下一项

当前版本、软件和旧真机证据以[统一路线图](architecture/CONTROLLER_ROADMAP.md)为准：软件契约已有基础，尚无稳定收益结论，KV真实动作尚未通过。当前唯一主线选第一项Instance，先完成前置资格与容量/启动标定、修正工作量核验，再冻结首个收益对照。暂不同时实施路由、KV新策略或通用协调器；旧Request作为共同能力保留，SWE/B1收益验证继续暂停。

本轮仅更新规划和任务顺序，不启动资源或模型。以后资源按已明确批准的具体范围，每窗口独立固定对象、权限和绝对截止；不动shuhao或他人活跃/未知资源，不修改共享平台，不延长历史窗口。网站、论文投稿及其他发布另依明确授权；已授权代码推送和主计划维护继续按原边界执行。
