# 图执行与分层缓存下的 P/D 服务场景模拟

2026-10-27。模型为 Qwen2.5-7B-Instruct、BF16、2P2D、TP1，目标硬件为两台各两张 64 GiB Ascend 910B2 的机器。

本阶段采用追求服务效率的参考配置：P/D 两端连续批处理、NPU 自动前缀缓存、图执行、按整卡资源预算分配 KV，以及异步的 CPU 保存、RDMA 交接和 NPU
恢复。结果是组件标定支持的架构场景预测，尚未经过完整两节点连接器验收。

## 参考配置

| 项目               | 设置与依据                                                                           |
| ------------------ | ------------------------------------------------------------------------------------ |
| 图执行             | `enforce_eager=False`，使用现有 graph2048 单引擎标定                                 |
| P/D 每实例并发上限 | 128，两端均通过同一引擎连续批处理                                                    |
| P token 预算       | 8192，另测已标定的 2048 对照                                                         |
| D token 预算       | 2048，运行请求优先、按剩余预算准入等待请求                                           |
| NPU KV             | 每实例 38 GiB，按 90% HBM 预算估算，实跑时以初始化内存 profiling 为准                |
| CPU 缓存池         | 每实例 24 GiB，同节点两实例共 48 GiB，按容器 64 GiB RAM 预留 16 GiB 余量             |
| 前缀复用           | 优先使用 NPU APC，其次使用 CPU 缓存；D 获得 P 已完成的全部可恢复块                   |
| 缓存传输           | P 的 NPU→CPU 保存、CPU→CPU RDMA、D 的 CPU→NPU 恢复分别排队；默认允许 DMA 与计算重叠  |
| 请求和路由         | 保留原 95 条请求、8 个会话、约 0.49 req/s 名义到达时间及同会话完成依赖；会话固定 P/D |
| 输出               | P 1 token，D 128 token，沿用原工作负载以便对照                                       |

NPU 内存预算依据：实测 graph2048、16 GiB KV 时 HBM 峰值 35,370 MiB，非 KV 部分约 18.54 GiB。使用 `floor(64×0.9−18.54−1)`
得到 38 GiB KV，额外预留 1 GiB。大 P token 预算可能增大 workspace，真实启动需要重新 profiling。CPU 预算同样需要结合两进程实际 RSS
与锁页缓冲区调整。

生产调优应在 TTFT/TPOT 目标内提升吞吐与资源效率。vLLM 文档指出，较大 token 预算倾向于提高吞吐与 TTFT，2048 等较小预算适合控制生成间隔；并发与 KV
容量也需要联动调节。参考 [vLLM 调优指南](https://docs.vllm.ai/en/latest/configuration/optimization/) 和
[Ascend ACL Graph](https://docs.vllm.ai/projects/ascend/en/v0.18.0/developer_guide/Design_Documents/ACL_Graph.html)。这些参考说明调优方向，具体预算来自本项目硬件与标定范围。

## 初步预测

TTFT 百分位曲线、基线调度说明与阶段耗时拆分见 [TTFT 分析](TTFT-ANALYSIS.md)。

| 场景                          | 平均 TTFT | TTFT p95 | TTFT p99 | 平均 TPOT | 全部完成 |
| ----------------------------- | --------: | -------: | -------: | --------: | -------: |
| P8192 / D2048                 |   0.247 s |  0.502 s |  0.970 s |  19.60 ms | 202.34 s |
| P2048 / D2048，已标定预算对照 |   0.258 s |  0.571 s |  1.086 s |  19.61 ms | 202.34 s |
| P8192 / D2048，拷贝与计算串行 |   0.257 s |  0.594 s |  0.985 s |  19.68 ms | 202.34 s |

95 个样本的 nearest-rank p99 等于最大值。TPOT 指每请求 `(完成−首 token)/127` 的统计，不能据此推出逐 token ITL 分布。

P8192 场景有 21 个计算步的 token 数超出 2048 标定范围；P2048 对照没有超过 token/序列标定范围的计算步。P8192
的结果应作为外推预测。单引擎模型的既有验证误差不构成完整 P/D 模型的误差保证。

这些数值的前提是完整目标流程中的异步交接、缓存层次和并发引擎语义得到实现。它们与前一阶段保留历史控制器和恢复成本的模拟，属于不同的服务流程假设。图模式、APC、P
并发、交接锁和服务成本模型同时发生变化，不能把数值差额全部归因于某个配置开关。

## 从结果看负载与瓶颈

- 原名义注入最后一条请求的时刻为 197.47 s，完成全部请求为 202.34 s。该场景基本跟随请求到达速度运行，没有持续增长的服务队列。
- 上限为 128 时，全系统实际在途峰值为 6；每实例实际运行峰值为 P0=1、P1=1、D0=3、D1=3。P 支持批处理，低到达速率下没有同时积累多个 P 请求。合成契约测试另外验证了 P、D
  两端都能批处理。
- 同会话完成依赖使这份 8 会话输入最多产生 8 条在途请求。提高并发上限不能增加它的独立会话数。并发上限 8 与 128 的预测结果一致。
- NPU 完整缓存块的驻留峰值约为 3.24–4.43 GiB，CPU 池峰值约为 3.25–4.20 GiB，两侧淘汰次数均为 0。把 NPU KV 从 38 改为 16 GiB
  的对照结果也相同。这说明该负载的工作集能完整驻留。
- P 共补算 141,798 token，D 共补算 5,990 token。其余前缀优先由 NPU APC 复用，D 只处理完整块之后的 logits 后缀。
- RDMA 总量约为 7.25 GiB，按历史网络服务系数累计约 0.924 s，最大单次负载约 403.7 MB，最大单次服务约 45.2 ms；该 FIFO 模型未出现 RDMA
  排队。当前负载不能建立网络拥塞主导延迟的证据。
- 按模拟的计算步占用时间统计，P0/P1 约为 3.55%/2.78%，D0/D1 约为 47.76%/45.02%。这是调度时间占用，**不是 AI Core
  利用率预测**。实际硬件利用率需要实测。

下一轮性能研究应在这套服务配置下扩大独立会话数，并使用真实请求产生的 KV 流量逐步提高负载。先确认服务饱和点，再区分计算、缓存容量、恢复路径和 RDMA 排队的影响。已有 95
请求可以保留为低负载功能与时序参照。

## 成本来源与边界

- 计算：使用 `pegaflow-step-simulator-20261026` 的图模式非负步成本模型，32 个标定输入、私有/共享两组，1326 个标定步。目标 95 请求的延迟没有进入拟合。
- CPU 保存与恢复：使用独立组件测试的 native `save_RPC_seconds`、`load_complete_seconds` 和 query 时间，按 token
  数分段插值。完整模型连接器下的额外开销、CPU 竞争和计算/拷贝重叠需要补测。
- RDMA：使用原实验冻结的 P→D 每字节服务成本，保留 CPU 缓存包粒度与 FIFO 服务队列。没有实现交换机队列、PFC/ECN 或 packet 级拥塞模型。
- 初始 CPU 缓存保留原实验库存，NPU 请求前缀从冷状态开始，模型与图执行视为已经预热。
- GPU 缓存复用、活动页引用和淘汰使用 `step_simulator.KVPool`；P 的活动页保留至 CPU 保存完成，RDMA 源 CPU
  块在传输期间固定。若需要未标定的抢占，模拟会报错。
- 该服务流程要求实际运行器支持请求级异步交接，并调整历史整次 API 锁。当前结果用于确定实现与补测方向，不能作为已有连接器的可交付性能成绩。
- 本轮未运行 Tailguard 优化调度处理组。调度算法效果需要在同一服务架构、容量和注入负载下另作对照。

## 文件与复现

`summary.json` 汇总全部五组配置；`per-request.csv` 保存逐请求指标。`graph-*.json.gz` 保留逐步计算、缓存计数和传输时间线，`inputs/`
保存数值输入及成本模型，`provenance/` 保存对应源码快照。

在 PegaFlow 工作区，将 `<report>` 替换为本目录：

```sh
python scripts/issue23/pd_serving_simulator.py \
  --inputs <report>/inputs \
  --step-model <report>/inputs/step-cost-model.json \
  --components <report>/inputs/components.json \
  --p-tokens 8192 --d-tokens 2048 --max-sequences 128 \
  --output <new-output>.json.gz
```

相关 30 项单元测试及 Ruff 通过；95 请求的会话因果顺序、P 完成后交接、各引擎 token 预算、资源排队时序通过检查。
