# MuxPD 默认模式 vs native：真实文本 workload 单轮性能验证，TP2 / TP4（2026-11-07）

**范围说明（请先读）**

- **派生负载**：请求正文取自真实文本（LongBench v1 qasper、OASST1），但到达过程（Poisson）、长短请求比例和固定输出长度（ignore_eos）
  都是本轮的测试设置。它不是原生任务执行（不评分、不看生成内容），也不是生产流量或原始请求回放。
- **单轮测量**：四种配置各回放三个 workload 一次，没有轮间方差，差异按实测报告，不作显著性结论。
- **结果有得有失**：中等负载场景（A）在 TP4 上 Goodput 退化；高负载场景（B）中 MuxPD 仍出现超过 0.5 s 的停顿； ITL p50 在全部对比中都增大；3 条超长
  qasper 样本因上下文容量被排除。见第 5-7 节。

本轮是 `vLLM-HUST/vllm-ascend-MuxPD-hust#36`（报告
`reports/muxpd-perf-default-vs-native-20261107`，#635）的后续， 只验证默认模式性能：不测 ROW，不设答题质量或 token 一致性门槛，不扩展
TP8 或其他模型，不重跑 13 个合成负载。

## 1. 从 #36 选出的场景类别

依据 #36 原始结果（`results/perf36-tp{2,4}/{native-s16,mux43-s16}/pass1`），并按请求类型复核了 SLO
违规原因（`data/bykind36.py`）。 选择时同时看 TP2 与 TP4、吞吐、Goodput、TTFT、TPOT 和停顿，不以单一最好的一行为准。

| ------------------------------------------ | ------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| A 长文档 prefill + 短对话 decode，中等负载 | mixed-r1.0    | Goodput s2/s3 约 20% -> 72-79%；native 违规以 0.5 s 最大间隔为主，MuxPD 消除 | TTFT p50 +30-60%；TP4 s1 Goodput 98.3% -> 87.4%（TTFT 越过 1 s） |
| B 同上，高负载                             | mixed-r1.6    | Goodput 0.5-7.8% -> 62-73%；TPOT p50 -30-40%；s2 吞吐 +5-6%                  | ITL p50 约 2 倍                                                  |
| C 纯短对话，过载                           | short-r2      | 吞吐 TP2 +6-8%、TP4 +9-10%；TPOT p50 -8-11%                                  | Goodput 两边都接近 0（仅 0 -> 5-8%），属饱和吞吐场景             |

未选：contend（TP2 吞吐 -7%、TPOT +16%，TP4 Goodput 下降，是代价场景）、burst（收益小、ITL p99 变差）、 short-r4（与 C 同类、更深饱和）。A
被选入是为了检验其收益与代价在真实长度下是否仍然成立，而不是因为它已确定有利。

## 3. 测试设置（运行前冻结：`data/PLAN.md`，`data/PLAN.sha256`）

- 栈：Qwen3.5-35B-A3B BF16，910B2；Core `d0f22d2`，Ascend `c182a9e`，MuxPD main
  `43fcaf4`（干净）。`HCCL_DETERMINISTIC` 未设置； 四个配置运行期间 NPU keepalive 均已停止，结束后恢复。
- 顺序：每次只有一个服务（端口 8300）。TP2 用卡 0,1：MuxPD 默认，然后 native；TP4 用卡 0-3：MuxPD 默认，然后 native。 每个配置依次回放三个
  workload 各一次。13:30-14:11 UTC 连续完成（`data/driver.log`）。
- 共同参数：max-num-seqs 16，max-model-len 16384，不开 prefix cache，gpu-memory-utilization 0.85； 图模式 compile
  mode 3，FULL_DECODE_ONLY，graphs [1,2,4,8,16]。
  - MuxPD 默认：`scripts/serve-qwen35-muxwise.sh`（async decoupled scheduler / worker，isolated overlap
    q4，decode graph， 不做 chunked prefill，16384-token 预算）。
  - Native：`tools/serve-native.sh --max-num-batched-tokens 16384`（chunked prefill 和 async scheduling
    为 native 默认值）。
  - 启动身份：`data/wl37-*.identity.txt`。以上与 #36 完全相同。
- 负载生成：未修改的 `data/loadgen.py`（流式，temperature 0，ignore_eos）；计划 JSON 多出的 `src` 字段不会被读取。 超时：服务健康等待 1800
  s，单请求 1800 s，单计划 `timeout 2400`。
- SLO / Goodput：`data/aggregate.py` 中 `slo()` 未改：TTFT \<= 1 s（长请求 3 s），TPOT \<= 0.1 s，最长 token 间隔
  \<= 0.5 s； Goodput = 满足全部三项的请求数 / 计划总请求数。
- 运行记录：四个服务都是第一次启动即健康；0 个计划失败；12 个结果、共 1968 个请求，0 个请求错误；最大发送滞后 0.025 s。 native TP2 服务日志中唯一的
  Traceback 是最后一个计划结束后按计划 SIGTERM 关闭引擎时产生的（`EngineDeadError`，在 shutdown 日志之后）。

## 6. 代价（本轮仍然存在）

- 轻中负载 TTFT 更高：A 中 TTFT p50 +53%（TP2）/ +46%（TP4），p99 1.03 -> 1.16 s、0.78 -> 1.13 s；B 中 TTFT p50 +16%
  / +22%。 TP4 A 的 Goodput 退化（短请求达标 92/93 -> 84/93）全部来自短请求 TTFT 越过 1 s（违规 1 -> 9），与 #36 TP4
  mixed-r1.0-s1 的机制相同。
- 典型 token 间隔变大：ITL p50 在全部 6 组对比中都更高，A +12~23%，B 和 C 约 1.7-2.0 倍（例如 TP2 C 26.2 -> 50.8 ms）。 TPOT
  已包含这一点，但 B / C 的 TPOT p50 仍然更低。
- 中等负载吞吐没有变化：A -0.6% / -0.1%，在单轮波动范围内。
- B 中 MuxPD 的残余停顿（见上表）说明，当长 prefill 在短时间内连续到达时，“不停顿”这一性质并不绝对。

## 7. 有效性与局限

- 单轮测量：每个配置每个 workload 只跑一次，同一 TP 内依次运行（MuxPD 先）。顺序与时间漂移无法和配置效应分开。 #36 已观察到跨天 TPOT p50 漂移达
  +12~38%；本轮四个配置在同一天约 40 分钟内完成，未与其他日期的数据混合。 几个百分点的差异（A 的吞吐、A 的 TPOT p50）不应解读为效果。
- 样本量小：A 长请求只有 19 个，TP4 A 的退化来自 8 个请求的差异；不对单个 workload 的小幅变化作推广。
- 派生负载：到达过程（Poisson）、速率、长短比例是沿用合成场景的派生参数，不是原始到达；输出长度由参考文本长度派生并用 ignore_eos 强制，
  模型实际生成内容不影响长度。结果代表“真实输入长度 / 真实多轮历史 + 派生到达”，不代表任何生产流量。 BurstGPT 等仅含长度与时间的元数据没有被当作请求正文。
- 上下文容量：max-model-len 16384（两臂一致）排除了 3 条 qasper；更长的文档（LongBench v2 等）不在本轮范围内。
- 已知的设计差异：MuxPD 不分块 prefill，native 使用 chunked prefill；调度器 / worker 类不同。
- 范围：一个模型，TP2 / TP4，三个 workload；不含质量、ROW、TP8。

## 8. 复现

```sh
# 数据：按清单固定版本取得，校验 data/source-files.sha256
#   LongBench data.zip（5e628be）中的 data/qasper.jsonl；dataset2prompt.json / dataset2maxlen.json（2e00731）
#   OASST1 validation parquet（fdf72ae），转为 jsonl（pyarrow 18.1.0，to_pylist 后逐行 json.dumps(default=str)）
python -I data/build_plans.py <data-raw> plans         # 运行前校验源文件 SHA256；输出 plans/*.json + MANIFEST.json
sha256sum -c data/plans.SHA256SUMS                     # 计划文件身份
bash data/run.sh                                       # 四个配置依次运行（服务脚本见 data/serve-*.sh），结果写入 results/wl37-tp{2,4}/{mux43,native}/pass1
python -I data/compare.py summary.json                 # 生成本报告中的表格
```
