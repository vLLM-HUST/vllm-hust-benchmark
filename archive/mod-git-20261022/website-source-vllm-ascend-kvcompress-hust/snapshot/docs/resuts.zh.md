# 当前基准测试结果

[English](resuts.md) | 简体中文

本文是当前仓库版本唯一的公开基准测试结果摘要。README 不再记录 A/B
结果表；复现命令和报告规则独立维护在[基准测试指南](benchmarking.zh.md)中。

## 状态

当前实现已在单张 Ascend 910B2 的 ACL graph 模式下通过功能、容量和在线
服务验证。所有 TriAttention 测试均确实执行了压缩，全部请求完成，被测
8192-token 提示由 64 个物理 block 压缩到 16 个。

主要结果依赖具体负载：

- 长上下文总 token 吞吐提升 **10.25%**；
- 高并发 KV 压力场景吞吐提升 **4.68%**；
- 短 prefix 负载基本持平，变化为 **+0.01%**；
- 短 random 负载仍有 **-1.25%** 固定开销；
- 64-case 长上下文召回测试从 64/64 变为 63/64，下降
  **1.5625 个百分点**。

这一质量下降需要被明确对待：当前 2048-token budget 在该 64-case 测试上
不满足“下降不超过 1 个百分点”的假设门槛。因此这些数据支撑工程验证结论，
不是通用性能或质量保证。

## 端到端 A/B 结果

所有数值来自匹配的单次运行。总吞吐同时包含 prompt 和 output token，延迟是毫秒均值，
变化值均为 TriAttention 相对 baseline 的变化。

| 场景 | 请求数 x 实际输入/输出 | 总 tok/s，baseline 到压缩 | 变化 | TTFT，baseline 到压缩 | TPOT，baseline 到压缩 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Prefix repetition | 4 x 2560/256，c=1 | 336.77 到 336.82 | **+0.01%** | 381.27 到 372.04 | 30.91 到 30.94 |
| Random | 2 x 2560/32，c=1 | 1522.03 到 1502.95 | **-1.25%** | 358.53 到 367.05 | 30.82 到 31.24 |
| Long context | 8 x 8192/256，c=4 | 2215.61 到 2442.73 | **+10.25%** | 1770.26 到 1791.57 | 47.86 到 42.27 |
| KV pressure | 16 x 8192/64，c=16 | 5787.01 到 6058.10 | **+4.68%** | 10497.88 到 10592.61 | 156.12 到 161.26 |

四组压缩负载共 30/30 请求成功，0 失败。每个 A/B pair 持久化的输入/输出长度
完全一致。prefix 和 long-context 客户端实际使用 benchmark 快照的通用
256-token 输出长度；表格记录原始结果中的实际长度，而不是传入客户端的
更小专用覆盖值。

## 容量与有状态压缩

每个 8192-token 提示的已提交 plan 均将物理 cache 从 64 个 block 降至 16 个，
并归还 48 个 block。在 block size 128 时，这表示物理 prompt KV 从 8192 减少到
2048，降幅为 **75%**；语义长度仍为 8192。

同一请求上也观测到了重复压缩：

- 语义长度 2560 时，20 个物理 block 降至 16 个，归还 4 个；
- decode 到语义长度 2688 后，17 个物理 block 再次降至 16 个，再归还 1 个。

这证明当前 runtime 不再只能执行一次 final-prefill 压缩事务。

allocator 会在服务启动时预留 KV 池，因此归还 block 通常不会降低 `npu-smi`
显示的进程级 HBM。归还 block 数、提交后的物理 token 以及活跃 KV 池占用才是
正确的容量信号。

## Kernel 微基准

以下 NPU 时间对比了旧的通用热路径与当前优化路径：

| 热路径 | 旧路径 | 当前路径 | 加速比 |
| --- | ---: | ---: | ---: |
| K/V 写入 | 0.582 ms | 0.330 ms | 1.76x |
| Paged-key 打分 | 1.258 ms | 0.728 ms | 1.73x |

offset tensor 操作本身为 0.055 ms。decode 路径的收益主要来自避免每 step 的
CPU→NPU offset 刷新和第二次完整 slot-mapping 计算。

微基准隔离了单个 kernel，本身不能预测端到端收益；在线服务结果应以上方
A/B 表为准。

## 正确性与质量

- Python 全量测试：**44 passed**。
- Ruff：通过。
- `git diff --check`：已验证实现快照通过。
- Ascend kernel 编译和数值 smoke：通过，与通用打分路径的差异在设定容差内。
- 长上下文召回测试：baseline **64/64（100%）**；压缩
  **63/64（98.4375%）**。

全层打分、通用打分实现和专用 kernel 都复现了同一个失败 case，因此没有将
质量差异隐藏为 kernel 数值误差。当前默认保留四层步进打分，以获得更高的在线服务
性能。需要更严格质量护栏的负载应评估更大 KV budget、不同校准统计或自适应
策略。

## 结果边界

这些是当前单设备、单模型和一组负载的工程测试结果，不能证明：

- 跨模型或跨平台加速；
- 进程级已分配 HBM 降低；
- 任意 KV budget 下都具备生产质量；
- 已支持多设备、async、推测解码、混合/MLA 或量化 KV；
- 已通过正式第三方验收。

以后更新结果时应直接替换本摘要，不在此追加带日期的历史。带日期的命令、原始
输出、失败尝试、机器路径和中间分析应放在 `docs/dev/` 下。
